High-level design concepts, grounded in this code

The Day-3 vocabulary, each with a short what, a why, and where it shows up here - marked [BUILT] (real and runnable) or [CONCEPT] (designed-for via a seam + notes, not implemented, to fit the one-day build).

The one idea that ties it together: every boundary that would be a network hop in real Instagram is a Java interface (a "port") here. Swapping the local implementation for a distributed one is then a change at one wiring point, not a rewrite. That is what makes a modular monolith "microservice-ready".

Foundations

HLD vs LLD. High-Level Design is the boxes-and-arrows view (which services, which datastores, how they talk). Low-Level Design is classes, methods, schemas. This project is mostly LLD you can run, arranged so the HLD boxes are visible as packages.

Client-Server. A client sends requests; a server holds the data and logic and responds. [CONCEPT] Our ui/ConsoleGateway is the "client"; the services are the "server". In a web version the gateway becomes REST controllers.

API / Request-Response. An API is the contract a server exposes; the client sends a request and gets one response. [BUILT, in miniature] InstagramService is our API surface; each method is a request/response.

Monolith vs Microservices. A monolith is one deployable; microservices are many small independently-deployable services. [BUILT as a modular monolith] One process, but split into bounded-context packages (user, post, feed, ...) that talk only through ports or the event bus - the seams along which you'd carve out services later.

API Gateway. A single front door that routes to services, and often does auth, rate limiting and aggregation. [CONCEPT] ConsoleGateway plays the role; a real one would sit in front of the REST APIs.

Data

SQL vs NoSQL. SQL databases are relational (tables, joins, constraints, transactions); NoSQL trades some of that for scale/flexibility (key-value, document, wide-column, graph). [BUILT] We use SQL (SQLite) for the normalized core. The repository port is what lets you move a context to a different store.

Normalization. Store each fact once, linked by keys - no duplication, strong integrity. [BUILT] See schema.sql: users, follows, posts, likes, comments are normalized with foreign keys.

Denormalization. Deliberately duplicate/precompute data to make reads fast. [BUILT] posts.like_count/comment_count, users.follower_count, and the materialized feed table. The cost - keeping copies in step on every write and tolerating brief drift - is paid by the services and is the core trade-off to teach.

CAP theorem. Under a network partition you can keep Consistency or Availability, not both. [CONCEPT, reflected in design] Follows/auth want consistency (CP); the feed and counters are fine being eventually consistent (AP) - which is exactly why they're denormalized and updated asynchronously via events.

Replication. Keep copies of data on multiple nodes for durability and read scaling (often one primary for writes, replicas for reads). [CONCEPT] Reads go through the repository port, so a read-replica adapter could serve them.

Sharding. Split one dataset across nodes by a key (e.g. user_id % N) so no single node holds everything. [CONCEPT] A ShardRouter would sit behind the repository port and pick a shard by key; cross-shard queries (like the social graph) are the hard part, which fan-out-on-write sidesteps at read time.

Performance & scale

Cache. A fast store in front of a slower one, holding hot data. [BUILT] platform/cache + read-through caching of feeds in FeedService; invalidated on new posts. The port is the Redis swap-in point.

CDN (Content Delivery Network). Edge servers that cache static assets (images, video) near users. [CONCEPT] Our posts store a media_url; in production that URL points at a CDN, not our app.

Message Queue. A broker that decouples producers from consumers and lets work happen asynchronously. [BUILT in-process] EventBus + InProcessEventBus. PostCreated has three independent subscribers (feed, notifications, search). Swap the in-process bus for Kafka/RabbitMQ and those become separate services.

Load balancer. Spreads incoming requests across many identical server instances. [CONCEPT] Works only if the servers are stateless - which our services are (all state is in the repositories), so N copies could run behind one.

Scalability - vertical vs horizontal. Vertical = a bigger machine (simple, capped, single point of failure). Horizontal = more machines (harder, needs statelessness + sharding, but scales far). [CONCEPT] The whole ports design targets horizontal scaling.

Availability / Reliability / Fault tolerance. Availability = the fraction of time the system responds. Reliability = it responds correctly. Fault tolerance = it keeps working when a part fails (via redundancy - replicas, retries, queues). [CONCEPT] The message queue and read replicas are the levers.

The feed, concretely (fan-out on write)

The signature scaling decision, and it's [BUILT]:

  • On a new post, FeedService fans the post out into the author's and every follower's materialized timeline (feed table).
  • Reading a feed is then a single indexed lookup - no join across follows and posts.
  • Trade-off / write amplification: a post by someone with a million followers is a million writes. The celebrity problem. [CONCEPT] Real systems use a hybrid: fan-out on write for normal accounts, fan-out on read (pull) for huge accounts, merged at read time.
  • Following someone does not backfill their old posts - honest fan-out-on- write behaviour, visible in SeedData (follows are set up before posts).

Security (Day-3 afternoon)

Authentication = who are you (login). Authorization = what may you do (permissions). [CONCEPT] Our console has a simple "logged-in user" session (InstagramService.login/currentUser) but no passwords or permission checks - the seam is the session; real auth would issue and verify tokens at the gateway.

Rate limiting. Cap how many requests a client may make in a window, to protect the system. [CONCEPT] Would live at the gateway (e.g. a token-bucket per user) before requests reach the services.
