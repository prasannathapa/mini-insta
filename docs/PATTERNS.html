OOP, SOLID & design patterns in this codebase

For each principle/pattern: what it is, why it matters, and where it lives here (with the checkpoint tag that introduces it). Everything points at real files, so you can read the pattern in context.

SOLID

S - Single Responsibility Principle

A class should have one reason to change.

  • Entities (user/User, post/Post) hold data and protect their own invariants - nothing else.
  • Services (post/PostService, graph/GraphService) hold one use case each.
  • Repositories only store and fetch.
  • ui/ConsoleGateway only does input/output; it contains no business logic.

Contrast: an early instinct is to put "follow", "post", "notify" all on User. Splitting them is why the notification logic could later move behind an event without touching User at all.

O - Open/Closed Principle

Open for extension, closed for modification.

  • Add a new feed ranking -> add a FeedRankingStrategy, change nothing else (feed/).
  • Add a new delivery channel -> add a NotificationChannel, change nothing else (notification/channel/).
  • Add a new post type -> add a subclass and one switch arm in PostFactory (the compiler finds every place that must change, because Post is sealed).

L - Liskov Substitution Principle

Subtypes must be usable anywhere the base type is.

  • The sealed Post subtypes are true substitutes - the feed, factory and repository all work on Post.
  • The clinching proof is PostRepositoryContract / UserRepositoryContract: the same test suite passes against both the in-memory and SQLite adapters (step-09-sqlite). If SQLite behaved differently, the shared test would fail.

I - Interface Segregation Principle

Many small interfaces beat one fat one.

  • UserRepository, PostRepository, FollowRepository, ... are each just the handful of methods that one context needs. PostRepository grew its like/comment methods only when PostService actually needed them (step-04-services), not before.

D - Dependency Inversion Principle

Depend on abstractions, not concretions.

  • Every service takes ports (interfaces) in its constructor, never a concrete store. AppContext is the single place that chooses concrete adapters.
  • Payoff: switching the whole app from in-memory to SQLite is one flag (-Dmini.store=sqlite) and zero changes to any service (step-09-sqlite).

Creational patterns

Factory - post/PostFactory (step-05-factory)

  • What: one place that turns a PostType + fields (PostRequest) into the right Post subclass.
  • Why: callers never write new PhotoPost(...); adding a type is localized. The switch is exhaustive over the sealed type, so the compiler enforces completeness.
  • Where: PostFactory.create(...), used by PostService.create(...), which every posting path funnels through.

Singleton - app/AppContext (step-03-ports)

  • What: exactly one composition root, created once at start-up.
  • Why: a composition root is genuinely global. Note the honesty in the code comments: elsewhere a Singleton is usually a hidden global and an anti-pattern. Services are not singletons reaching into globals - they receive their dependencies via constructors.

Structural patterns

Facade - app/InstagramService (step-04-services)

  • What: one simple interface over the user/graph/post/feed/story/search/ messaging/notification contexts.
  • Why: the console (and any future REST layer) calls one class; a "like" or "follow" quietly orchestrates several contexts behind it. Each service stays ignorant of the others.

Adapter - notification/channel/ (step-07-adapter)

  • What: EmailNotificationAdapter and SmsNotificationAdapter wrap third-party APIs (LegacyEmailClient.sendEmail(...), SmsGateway.push(...)) whose shapes don't match our NotificationChannel.
  • Why: the app delivers through one interface; the mismatched external APIs are hidden behind adapters. ConsoleNotificationChannel needs no adapter - it already speaks our language.

Behavioral patterns

Strategy - feed/FeedRankingStrategy (step-08-feed)

  • What: ChronologicalFeedStrategy vs EngagementFeedStrategy, swappable at runtime via InstagramService.setFeedRanking(...).
  • Why: the ranking algorithm changes independently of how feeds are built or read. The console's "toggle feed ranking" shows it flip live.

Observer / Publish-Subscribe - platform/events/ (step-06-events)

  • What: PostService publishes PostCreated to an EventBus; the feed, notification and search contexts subscribe and react.
  • Why: the publisher doesn't know who listens. Three independent consumers react to one event. This is also the message-queue seam (see HLD.html).

Also worth pointing out

  • Records for immutable values: Comment, Notification, DirectMessage, Follow, FeedEntry, PostRequest.
  • Sealed hierarchy + pattern matching: Post and the exhaustive switch in PostFactory, SqlitePostRepository and Main (early steps).
  • Dependency injection of java.time.Clock: every time-dependent behaviour (story expiry, feed recency) is deterministic in tests because the clock is injected, never read from the wall directly except in AppContext.
