Architecture

Mini Instagram is a modular monolith with microservice-ready seams: one runnable process, split into bounded contexts that talk only through ports and an event bus. Those are the lines along which you could later split real services. See PATTERNS.html for the OOP/GoF patterns and HLD.html for the scaling concepts.

The diagrams below are Mermaid. They render on GitHub, IntelliJ and VS Code (with Mermaid support). In a plain text viewer you will see the diagram source.

Layers (ports and adapters / hexagonal)

Everything above the ports is pure logic that depends only on interfaces (Dependency Inversion). Everything below is a replaceable adapter. AppContext is the one place adapters are chosen and the graph is wired.

flowchart TD
    UI["ConsoleGateway (REPL)"] --> FAC["InstagramService (Facade + session)"]
    FAC --> SVC["Stateless services:<br/>User, Graph, Post, Feed,<br/>Story, Search, Messaging, Notification"]
    SVC --> PORTS{{"Ports (interfaces):<br/>Repository, FeedCache,<br/>EventBus, NotificationChannel"}}
    PORTS --> MEM["In-memory adapters<br/>(default, and used by tests)"]
    PORTS --> SQL["SQLite adapters<br/>(run with -Dmini.store=sqlite)"]
    ROOT["AppContext<br/>(composition root)"] -. wires everything .-> FAC

In a web version, ConsoleGateway becomes REST controllers behind a load balancer, and the stateless services run as many instances.

Bounded contexts

Each is a package owning its data and rules. Cross-context references are by id, and cross-context communication is via the event bus, never by reaching into another context's tables.

The write path of a post (event-driven)

PostService saves the post and publishes one event. It knows nothing about feeds, notifications or search. Three independent consumers react. Swap the in-process bus for a real broker and they become separate services.

sequenceDiagram
    actor User
    User->>PostService: create(request)
    PostService->>PostRepository: save(post)
    PostService->>EventBus: publish(PostCreated)
    EventBus->>FeedService: onPostCreated
    EventBus->>NotificationService: onPostCreated
    EventBus->>SearchService: onPostCreated
    FeedService->>FeedRepository: fan out into follower timelines
    NotificationService->>NotificationChannel: deliver to each follower
    SearchService->>HashtagIndex: index the caption's hashtags

Persistence

Normalized core plus deliberate denormalization (counters and the materialized feed table). Schema: src/main/resources/schema.sql.

Two adapter families implement every repository port: in-memory (default, used by tests) and SQLite (-Dmini.store=sqlite). Stories, search and DMs ship with in-memory adapters only; their SQLite versions would follow the identical pattern (left as a student exercise).

Testing strategy

  • Contract tests (UserRepositoryContract, PostRepositoryContract) run the same behaviour suite against both in-memory and SQLite adapters, which proves substitutability.
  • Behaviour tests for each service (follow idempotency, like counters, feed fan-out and ranking, story expiry, hashtag search, DMs, cache hit/miss).
  • Deterministic time via an injected java.time.Clock (Clock.fixed(...) in tests), so 24-hour story expiry is tested in microseconds.

Where to change things

  • New feature/context: new package with its own port(s) and service, wired in AppContext, reacting to events if needed.
  • New storage backend: new adapter implementing the port; change one line in AppContext.
  • New feed algorithm: new FeedRankingStrategy.
  • New delivery channel: new NotificationChannel.
